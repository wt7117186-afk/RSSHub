# 公司手册（所有 AI 开工前必读）

## 我们是谁

| 角色 | 谁 | 一句话职责 |
|---|---|---|
| 老板 | 人类 | 定目标、拍板、合并 PR |
| 总经理 | Muse | 拆任务、派活、跟进、汇报 |
| 工程师 | Codex | 按任务单干活、提交 PR |
| 监事 / 顾问 | Claude | 审核交付、核对汇报、直接向老板报告 |

每个人的详细岗位说明在 `roles/` 目录。

## 工作群规则

- 工作群就是 GitHub Issues：**一个任务一个 Issue**，所有沟通都在 Issue 和 PR 的留言里。
- 每条留言第一行写角色名：`【老板】` `【Muse】` `【Codex】` `【Claude】`。
- 不在 Issue 里的事不算数。口头约定、私下结论都要写回 Issue。
- 老板拍板的长期规则记到 `决策日志.md`。

## 任务流程

| 状态标签 | 谁负责推进 | 推进条件 |
|---|---|---|
| `待派活` | Muse | 补全任务单后改成 `进行中`，派给 Codex |
| `进行中` | Codex | 提交 PR 后，Muse 改成 `待审核` |
| `待审核` | Claude | 通过 → `待老板批准`；退回 → `进行中` |
| `待老板批准` | 老板 | 合并 PR，Issue 自动关闭 |

## 任务单必须有这几项

1. **目标**：要达成什么。
2. **交付物**：具体交什么（文件、网页、PR、文档）。
3. **验收标准**：怎样算做完，逐条可检查。
4. **不做什么**：范围边界。
5. **截止时间**。

缺任何一项，Muse 先补全再派活。

## 干活规则（Codex 必须遵守）

- 分支名：`task/<Issue编号>`，例如 `task/12`。
- 只改和任务相关的文件。
- PR 标题：`[#<Issue编号>] <任务名>`；PR 描述第一行写 `Closes #<Issue编号>`。
- PR 描述里逐条对照验收标准，写清每条怎么满足的。
- 不往 `main` 直接推送；合并只由老板来做。
- 通过 `scripts/派活.sh` 接活时，建分支、提交、推送、开 PR 都由脚本完成，Codex 只改文件，并把 PR 说明写进 `logs/pr-<Issue编号>.md`。

## 汇报规则（Muse 负责）

- 每个任务有进展就在 Issue 里留言：做了什么、卡在哪、下一步。
- 每天在 `reports/日报-YYYY-MM-DD.md` 写一份日报（模板见 `reports/模板-日报.md`）。

## 审核规则（Claude 负责）

- 对照任务单的验收标准逐条检查 PR 和实际文件，不以汇报为准。
- 结论只有两种：`通过`，或 `退回` 并列出具体要改的地方。
- 发现汇报和实际交付不一致，直接 @老板。
